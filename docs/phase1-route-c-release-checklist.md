## Transaction and partial-failure assessment

Repository and installed dependencies agree: **drizzle-orm 0.45.4**, **drizzle-kit 0.31.11**, pinned in bun.lock. Source evidence:

- `drizzle-orm/migrator.js` reads journal entries and computes SQL hashes.
- `drizzle-orm/pg-core/dialect.js:44` selects timestamps newer than the initial ledger high-water mark, then executes **all selected SQL and their ledger inserts inside one session transaction**.
- `drizzle-orm/node-postgres/session.js:180` explicitly begins, commits on success and rolls back on error. The postgres-js session delegates the whole callback to `client.begin`.
- 0012 is a single DO block with no outer BEGIN/COMMIT, so it does not prematurely end that transaction. Its own exception also prevents partial changes within the block.
- The generated 0013 must not contain transaction-control statements. Its query has no business-data/schema effect; its intended persistent footprint is its normal migration record and generated files.

Under that standard runner, a failure in 0012, the companion or either ledger insertion rolls back the pending batch's function/trigger changes and new ledger rows. Success commits both. An ordinary “0012 committed, 0013 failed” state is **not expected under the inspected batch transaction**. Treat such a state as evidence of a different wrapper/boundary or another action; do not assume atomicity merely because two files ran in order.

**Filesystem and Git are not in the PostgreSQL transaction.** Generation may leave 0013 files/journal changes even if check or database execution fails. Conversely, SQL may commit successfully while the response, Git commit or GitHub synchronization fails. A timeout or tool error is not proof of database rollback. Establish the state by authorized read-only inspection before any retry.

The ledger uses SERIAL IDs. Failed transactions may consume sequence values, so after a safe retry there can be 14 rows without consecutive IDs. Compare hashes/timestamps and counts; never reset the sequence to make IDs look tidy. PostgreSQL documents that aborted transactions do not reclaim sequence values: [sequence behavior](https://www.postgresql.org/docs/current/functions-sequence.html).

### Recovery after a confirmed successful migration

The preferred action is targeted forward recovery, not deleting history. 0013 has no business effect to undo. Frontend rollback and database rollback are separate decisions; an older approved frontend can coexist with the migrated database.

If a confirmed backend issue requires restoring the original trigger/seed, pause writes and separately approve that recovery. The reviewed `docs/sql/phase1-fb-opex-rollback.sql` is a **standalone transaction script** and includes BEGIN/COMMIT. **Do not feed it verbatim into the managed Drizzle migration tool**, where COMMIT could end the runner's transaction before ledger insertion. Do not improvise removal of wrappers during a production incident.

For a fully tracked managed recovery, prepare/review/rehearse a **new forward rollback migration** containing the guarded rollback DO logic without outer transaction-control statements, with a fresh journal identity. If apply-only execution remains unavailable, use Route C again: merge that separately approved pending recovery file and trigger it with a separately approved harmless companion. With no intervening migrations, this would produce two additional natural records (14 → 16), not erase/reuse the old 0012/0013 identities. Exact new names/hashes/timestamps and any recovery tests must be approved before execution. No such files or SQL are created/executed by this assessment.

The rollback restores the known save-time defaulting defect and does not remove new scenario versions or repair historic assumptions. If later reapplying the correction is necessary, use another reviewed forward migration/normal runner plan; old 0012 is already logged and must not be forced pending by deleting its ledger row or changing its timestamp. Full backup restore is a last-resort separately approved operation with possible loss of later writes, not the default response to a companion or Git failure.
